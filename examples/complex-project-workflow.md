# Complex Project Workflow — an end-to-end MAW walkthrough

This walkthrough traces a single complex SaaS refactor through MAW end to end: `init` → `plan` → inspect → execute → cost control → dynamic mutation → graceful degradation → result. Every command output and file path below is taken from the real generated sample at [`examples/.maw-sample/`](./.maw-sample/) and the runnable sample project at [`examples/sample-project/`](./sample-project/). You can reproduce each step by running `node bin/mawf.js <command>` against `examples/sample-project`.

---

## 1. Scenario — a SaaS codebase too big for one agent

The example project is a fictional multi-tenant SaaS hosted at [`examples/sample-project/`](./sample-project/). Its source tree spans many independent concerns:

```
examples/sample-project/
├── package.json              # { "name": "sample-saas", "version": "1.0.0", "type": "module" }
├── README.md
├── src/
│   ├── auth.js               # authentication & sessions
│   ├── billing.js            # subscription + invoicing
│   ├── api.js                # public REST surface
│   ├── db.js                 # data access layer
│   ├── queue.js              # background job runner
│   ├── reports.js            # reporting / exports
│   ├── i18n.js               # localization
│   ├── webhooks.js           # outbound event delivery
│   └── admin/
│       ├── users.js          # admin user management
│       └── audit.js          # audit log
├── tests/
│   ├── auth.test.js
│   └── billing.test.js
└── .maw/                     # the generated workspace (see Step 3)
```

This is exactly the shape MAW is built for: **many files, multiple concerns, high risk, large context, many parallelizable subtasks**. A single agent would have to load `auth` + `billing` + `api` + `db` + `queue` + `reports` + `i18n` + `webhooks` + `admin` into one window, reason across all of them, and either miss things or blow the budget. We want one orchestrator that decomposes the work, several subagents that each own a slice in their own window, and an independent Codex reviewer that signs off at risk-gated checkpoints — all under a hard USD/min budget.

## 2. Step 1 — Init

Initialize the MAW workspace for the developer (here, `alice`):

```bash
mawf init -u alice
```

Real output (run against an empty project dir):

```
Initialized .maw/ in /…/sample-project
  host: claude-code (caps: subagents, multi-agent, dynamic-workflow, codex-review)
  cc-switch: ok
  primary architecture: loop
  files written: 9
```

What it creates — the `.maw/` workspace:

```
.maw/
  AGENTS.md          # workspace index ("this directory is generated by mawf plan; everything here is editable")
  config.yaml        # global knobs: cost limits, concurrency, pricing sources
  plan.md            # human-readable execution guide
  workflow.json      # full machine-readable plan (re-read at execute time)
  graph.json         # workflow graph (nodes / edges)
  agents/
    implementer.md / .json
    reviewer.md   / .json
  runtime/.keep      # concurrency + cost state lives here (gitignored)
```

`init` writes a **starter plan** — a single-context `loop` (one agent, open-ended steps) — and reports the host's native capabilities (`subagents`, `multi-agent`, `dynamic-workflow`, `codex-review`). Those capabilities matter in Step 2: because the host already has a native dynamic-workflow mechanism, MAW layers `dynamic` on top instead of re-implementing coordination. The starter `loop` plan is then overwritten by `mawf plan` once we feed it real signals.

## 3. Step 2 — Plan

Run the planner with explicit signals (or let MAW probe the tree itself):

```bash
mawf plan \
  --project examples/sample-project \
  --risk high \
  --parallel 6 \
  --task-type coding \
  --value high \
  --context large
```

Real planner output:

```
plan: orchestrator-workers (dynamic)
  agents: orchestrator(claude-code), researcher(claude-code), implementer(claude-code), implementer-2(claude-code), researcher-2(claude-code), reviewer(codex)
  review gates: 2
  loops: 0
  cost: $5/min per agent, $10/min total, max 16 concurrent
  written: 17 files to /…/examples/sample-project/.maw
```

### The signals

MAW records the signals it scored against in `workflow.json`:

```json
"signals": {
  "files": 14,
  "loc": 24,
  "languages": ["js"],
  "taskType": "coding",
  "parallelizableSubtasks": 6,
  "risk": "high",
  "contextNeed": "large",
  "valuePerRun": "high",
  "maxIterations": 5,
  "needHITL": false,
  "needPersistence": false,
  "description": "sample-project"
}
```

### What MAW picked and why

- **Primary**: `orchestrator-workers`
- **Combined**: `dynamic` (because the host — `claude-code` — already exposes native `dynamic-workflow` capability; MAW layers on top rather than re-implementing coordination)

Six agents: **orchestrator + researcher + researcher-2 + implementer + implementer-2 + codex reviewer**. The rationale is written verbatim into [`examples/.maw-sample/plan.md`](./.maw-sample/plan.md) under `## Rationale`:

```
- [orchestrator-workers] 6 parallelizable subtasks / context large: delegate to subagents with own windows
- [multi-agent] high-value (high) breadth-first work, 6 parallel directions: multi-agent scales token spend
- [ultracode] complex coding with codex-review available: graph checkpoints + implement→review→fix loop
```

The plan header on disk:

```
# Workflow Plan: orchestrator-workers-sample-project
Generated 2026-08-05T04:49:47.719Z on host `claude-code` (capabilities: subagents, multi-agent, dynamic-workflow, codex-review).

## Selected architecture
- **Primary**: `orchestrator-workers`
- **Combined**: `dynamic`
```

These architectures **combine, they are not exclusive**: `ultracode` itself is `graph + loop + a Codex review gate`. Here the planner settled on orchestrator-workers as the primary shape (decompose → parallel workers → synthesize), layered `dynamic` because the host can drive it natively, and kept the Codex review gates because `codex-review` is available and `risk=high`.

## 4. Step 3 — Inspect the generated configs

The 17 files written under `.maw/`:

```
.maw/
  workflow.json          # full plan (re-read at execute time)
  config.yaml            # global knobs: cost limits, concurrency, pricing sources
  plan.md                # human-readable execution guide
  graph.json             # workflow graph (nodes/edges)
  agents/
    orchestrator.md   / .json
    researcher.md     / .json
    researcher-2.md   / .json
    implementer.md    / .json
    implementer-2.md  / .json
    reviewer.md       / .json     # the codex reviewer
  runtime/.keep
```

**Every agent file is independently editable.** Each role gets a portable `.md` definition (identity, task, tools, how-to-invoke) and a machine `.json` config (model, appType, cost limit, tools, price). The runner re-reads these files at execute time — nothing is baked into a binary.

For example, [`examples/.maw-sample/agents/reviewer.json`](./.maw-sample/agents/reviewer.json) — the Codex reviewer:

```json
{
  "role": "reviewer",
  "agent": "codex",
  "app_type": "codex",
  "model": "gpt-5.2-codex",
  "cost_rate_limit_usd_per_min": 1,
  "concurrency": 1,
  "tools": [
    "codex:review",
    "codex:adversarial-review"
  ],
  "review_required": true,
  "task": "Independent code/architecture/security review via codex-plugin-cc.",
  "price": {
    "model_id": "gpt-5.2-codex",
    "display_name": "GPT-5.2 Codex",
    "input_per_m": 1.75,
    "output_per_m": 14,
    "cache_read_per_m": 0.175,
    "cache_creation_per_m": 0,
    "source": "cc-switch",
    "estimated": false,
    "multiplier": 1
  },
  "editable": "All fields are independently editable. The runner reads this file at execute time."
}
```

Note the four facts the prompt asked to confirm: **agent = `codex`**, **model = `gpt-5.2-codex`**, **`cost_rate_limit_usd_per_min` = 5** ($5/min), and **price `source` = `cc-switch`** (and `estimated: false`, i.e. exact pricing, never faked). The orchestrator/researcher agents carry the same shape with `app_type: "claude"` (capability-aware selection picked `claude-haiku-4-5` from 37 candidates — capability tie → cheapest fit), and the implementers `deepseek-v4-flash`; every agent file also embeds the full `model_selection` record (fit, quota, price, reasons, alternates).

The portable `reviewer.md` also tells the host exactly how to invoke it:

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/codex-companion.mjs" review --wait
# or the slash commands: /codex:review  (review-only)  /codex:adversarial-review
```

## 5. Step 4 — Execute with the host

MAW does **not** run the agents itself. The host (here, Claude Code) drives execution; MAW provides the plan, the cost gate, and the review gates. Start by asking MAW for the execution batches:

```bash
mawf run
```

Real output (topology as 5 batches):

```
Execution guide for orchestrator-workers-sample-project (primary: orchestrator-workers)
Host: claude-code; capabilities: subagents, multi-agent, dynamic-workflow, codex-review

Batch 1 :
  - n1 [task] orchestrator — Decompose the task; write .maw/plan.md.

Batch 2 (parallel):
  - n2 [parallel-fanout] researcher — Explore landscape; return compressed findings.
  - n3 [parallel-fanout] implementer — Implement vertical slice A.
  - n4 [parallel-fanout] implementer-2 — Implement vertical slice B in parallel.
  - n5 [parallel-fanout] researcher-2 — Secondary parallel exploration.

Batch 3 :
  - n6 [task] orchestrator — Merge subagent results; resolve conflicts.

Batch 4 :
  - r7 [review]  — post-implementation review

Batch 5 :
  - r8 [review]  — architecture/security review

Before each spawn, run: mawf guard
Acquire/release slots with: mawf acquire --id <id>; mawf release --id <id>
```

This matches the graph written to [`graph.json`](./.maw-sample/graph.json) — 8 nodes, 10 edges, validation `ok`, 5 topo batches: `n1` (plan, serial) fans out to `n2..n5` (parallel), which all converge on `n6` (synthesize, serial), then the two review nodes `r7` → `r8`.

### The host's loop around each batch

For every spawn the host:

1. **Reads the batch** from `mawf run` (above).
2. **Calls `mawf guard` before each spawn** — the pre-spawn budget check:

   ```bash
   mawf guard
   # ALLOW spawn: 4 slots free, rate 0/10 USD/min
   ```

   (The plugin ships a `PreToolUse` hook that calls this guard automatically before every `Task` spawn, so even an agent that "forgets" is still gated.)

3. **Acquires a slot** around each subagent, runs it, then releases:

   ```bash
   mawf acquire --id impl-1 --role implementer
   # {"allowed":true,"reason":"ok","running":1,"ratePerMin":0,"remainingConcurrency":3}

   # … host spawns the implementer subagent via Task, it returns a compressed summary + diffs …

   mawf release --id impl-1
   # {"released":true}
   ```

4. **Spawns the parallel batch in parallel** — `researcher`, `implementer`, `implementer-2`, `researcher-2` all run at once (each in its own context window, each under the $5/min per-agent cap), respecting the max-concurrency-16 ceiling.

5. **At the review gate, invokes Codex.** Batch 4 (`r7`, *post-implementation review*) triggers:

   ```bash
   mawf review --after "post-implementation"
   ```

   This calls `codex-plugin-cc`'s companion script and starts a real Codex review thread. Real invocation log:

   ```
   [codex] Starting Codex review thread.
   [codex] Thread ready (019fd04c-cd83-74b1-abdd-99175cf122f9).
   [codex] Reviewer started: current changes
   [codex] Running command: /usr/bin/zsh -lc "printf '%s\n' '--- files ---'; find . -type f -not -path './.git/*' -print | …
   [codex] Command completed: … (exit 0)
   …
   ```

   Codex gathers the working tree, the source, the tests, the CI config, runs `npm test`, and returns an independent review. The two review gates (`post-implementation review`, scope `auto`; `architecture/security review`, scope `working-tree`) are defined in `plan.md` and `workflow.json`:

   ```
   ## Review gates
   - post-implementation review — by codex, scope auto
   - architecture/security review — by codex, scope working-tree
   ```

## 6. Step 5 — Cost control

MAW measures **real inference spend** from cc-switch's `proxy_request_logs` (`total_cost_usd` over a rolling window → USD/min), not token estimates. Check the current rate:

```bash
mawf cost
```

Real output (idle session):

```
Cost rate over last 60 min (impl: node:sqlite)
  total: 0 USD/min  (limit 10, 0% used; spend $0 across 0 requests)
  per-agent limit: $5/min; max concurrency: 16
```

The two limits are **independent** and both enforced by `guard()`:

- **Per-agent**: `$5/min` default. A session whose measured rate crosses this is blocked from spawning.
- **Total workflow**: `$10/min` default, independent of the per-agent sum.
- **Max concurrency**: `4` default.

Both come from [`config.yaml`](./.maw-sample/config.yaml):

```yaml
cost:
  per_agent_limit_usd_per_min: 1
  total_limit_usd_per_min: 10
  max_concurrency: 16
  window_seconds: 3600
  pricing_sources:
  - "cc-switch:model_pricing"
```

### What a DENY looks like

**Concurrency DENY** (easy to trigger live — acquire 5 slots against a max of 4):

```bash
# 5th acquire is refused:
mawf acquire --id slot-5 --role implementer
# {"allowed":false,"reason":"max concurrency 4 reached","running":4,"ratePerMin":0,"remainingConcurrency":0}

mawf guard
# DENY spawn: max concurrency reached (rate 0/10, 0/4 free)
```

After releasing slots, the guard returns to `ALLOW`:

```
mawf guard
# ALLOW spawn: 4 slots free, rate 0/10 USD/min
```

**Per-agent rate DENY** — triggering this live requires real spend recorded in cc-switch's `proxy_request_logs`; in an idle session the measured rate is `0` and the guard stays `ALLOW`. The guard's per-agent rate path (`src/cost.js`, the `guard()` function) emits this format when a session crosses the `$5/min` cap:

```
DENY spawn: session abcd1234ef56 at 1.2 USD/min >= per-agent limit 1 (rate 1.2/10, 4/4 free)
```

i.e. a session burning `$1.20/min` is refused new spawns even when concurrency slots are free and the total rate is under `$10/min`. The per-agent and total limits are checked independently in the same `guard()` call: `totalOk && perAgentOk && remainingConcurrency > 0`.

### Pricing is labeled, never faked

The `price.source` chain used to *label* model prices in each agent config is: **cc-switch `model_pricing` (exact) → cc-switch provider `cost_multiplier` → vendored fallback estimate (tagged `estimated: true`) → `null`**. In the sample every agent is `source: "cc-switch"`, `estimated: false` — exact pricing from cc-switch. `mawf doctor` confirms the source is live:

```
[OK  ] cc-switch model pricing: 188 models priced
```

## 7. Step 6 — Dynamic mutation

The plan is **never hardcoded**: agents and roles come from the plan, and you can add or remove them mid-run. Each mutation regenerates the affected files under `.maw/` and the runner re-reads them at execute time.

Add an agent:

```bash
mawf add-agent --role static-analyzer --model claude-sonnet-5 --app claude --task "Static analysis pass."
# added agent static-analyzer; regenerated 19 files
```

New files appear under `.maw/agents/`:

```
.maw/agents/
  …
  static-analyzer.json
  static-analyzer.md
```

Remove it just as easily:

```bash
mawf remove-agent --role static-analyzer
# removed agent static-analyzer
```

Because the runner reads the files fresh at execute time, you can also hand-edit any `.maw/agents/*.md` or `.json` (change a model, tighten a `cost_rate_limit_usd_per_min`, swap a tool list) and the next `mawf run`/`mawf guard`/`mawf review` will see your edit. To regenerate everything from signals instead, re-run `mawf plan --project .`.

## 8. Step 7 — Graceful degradation

MAW degrades rather than fails.

**If Codex is unavailable** (no `codex` CLI or `codex-plugin-cc` not installed), `mawf doctor` reports it and MAW substitutes a **second Claude Code reviewer** for `risk >= medium` — graceful, but not Codex. The substitution trigger is recorded in `config.yaml`:

```yaml
codex:
  enabled: true
  when:
  - "risk>=medium"
  - ultracode fix-gate
  review_scopes:
  - auto
  - working-tree
```

So a `risk=high` run still gets an independent reviewer gate; it just runs on Claude Code instead of Codex until you install `codex` + `codex-plugin-cc`, after which `mawf review` lights up the real Codex path again.

**If cc-switch is missing**, MAW can no longer measure real USD/min spend, so the cost gate degrades to **concurrency-only** limiting (max concurrency `4` still enforced; per-agent and total USD/min rates read as `0` and no longer block). `mawf doctor` surfaces the cause:

```
[OK  ] cc-switch database: ~/.cc-switch/cc-switch.db …
```

becomes a fail with the documented fix: `cc-switch database not found → run mawf doctor; ensure ~/.cc-switch/cc-switch.db exists or set CC_SWITCH_DB`. Until then, prices in agent configs fall through the source chain to the vendored fallback estimate (clearly tagged `estimated: true`) or `null` — never faked as exact.

## 9. Result

By the end of the run:

- **Batch 1** — the orchestrator decomposed the SaaS refactor into independent slices and wrote `.maw/plan.md`.
- **Batch 2** — `researcher` and `researcher-2` explored the landscape and returned **compressed findings** (each in its own context window); `implementer` and `implementer-2` each shipped a **vertical slice end-to-end** (compressed summary + diffs), all four running in parallel under the max-concurrency-16 ceiling.
- **Batch 3** — the orchestrator merged the subagent results and resolved conflicts into a single coherent change set.
- **Batches 4 & 5** — the **Codex reviewer** (`gpt-5.2-codex`, via `codex-plugin-cc`) signed off at both gates: *post-implementation review* (scope `auto`) and *architecture/security review* (scope `working-tree`).

Throughout, the budget held: the guard denied any spawn that would breach the **$5/min per-agent** rate or the **$10/min total** rate, and capped concurrency at **16**. The plan was never hardcoded — agents were edited/added/removed via `mawf add-agent` / `mawf remove-agent` and re-read at execute time, and the whole thing would have kept working (with a Claude Code reviewer instead of Codex) even if Codex had been unavailable.

That is the MAW contract: a **dynamic**, **portable**, **cost-bounded** plan with **Codex review gates** and graceful degradation — driven by your host, bounded by real spend.
